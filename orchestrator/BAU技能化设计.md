# BAU 生成器 → Skill 抽象设计（路线 D）

> 前提：我们的程序 = 「LLM 调度层（路线 D 已搭好）+ 技能注册表 + Office 落盘」。
> 本文回答：BAU 文档生成器的功能能不能抽象成 skill？怎么抽象？

## 一、直接结论

- **能抽象成 skill 的**：Budget ROM、4Blocker、PBT 三个生成器，以及 Word→Excel 表格提取工具。
- **不应该 / 不能抽象成 skill 的**：**Hub 窗口**。Hub 是导航与入口，本质就是"路由层"，在我们的程序里由 `orchestrator`（意图路由 + 前端菜单）承担，不需要也不应该做成一个 skill——否则等于把"调度器"本身又塞回"被调度的技能"里，层次错乱。

## 二、功能 → Skill 映射

| BAU 原窗口 / 功能 | 是否 skill | 在路线 D 中的角色 |
|---|---|---|
| **Hub** | 否 | = orchestrator 路由层 + 前端入口（选技能 / 传参 / 上传文件） |
| **Budget ROM** | 是 | `budget_rom`：输入 2 个 Excel → 产出 Budget ROM 模板 |
| **4Blocker** | 是 | `four_blocker`：产出 4Blocker 文档 |
| **PBT** | 是（特殊） | `pbt`：执行体**必须包 verified 源码**，禁止猜测重实现 |
| **Word→Excel 提取** | 是（工具型） | `extract_tables`：被其他 skill 复用的 utility |

## 三、Skill 标准结构（与程序对齐）

每个 skill = 一个 Python 模块，含：

```python
SKILL = {
    "name": "budget_rom",
    "description": "根据项目背景与 AP 汇总两个 Excel，生成 Budget ROM 模板",
    "trigger": ["rom", "预算", "budget", "BAU"],
    "input_schema": {           # 槽位，前端据此渲染表单/上传
        "excel_1": "file",      # 项目背景 Excel
        "excel_2": "file",      # AP 汇总 Excel
        "output_format": ["xlsx", "docx"],
    },
    "prompt_template": "templates/budget_rom_prose.j2",  # 仅自然语言部分
    "run": run,                 # 调引擎函数，确定性产出文件
}
```

## 四、关键设计原则（决定成败，务必遵守）

1. **引擎与 UI 分离**
   从现有 Tkinter 代码里把"读 Excel → 算字段 → 填模板"的纯函数抽成 importable 模块（`engine/`）。桌面 App 和 Web skill **共用同一份引擎**，避免两份逻辑漂移、各改各的。

2. **LLM 不做数、代码做数**
   LLM 只负责两件事：① 理解用户一句话请求 → 选对 skill + 填槽位；② 生成文档里的**自然语言段落**（如说明文字）。真正的表格计算、字段映射、模板填充由确定性代码完成。**否则 BOM/ROM 数字会被幻觉，生产网文档出事。** 这是抽象成 skill 时最容易踩的坑——别让模型"生成"表格。

3. **PBT 严守"绝不猜测"**
   `pbt` skill 的 `run()` 直接 import 你**已验证的 PBT 源码**并实跑。在我读源码 + 实际运行验证之前，不写 PBT skill 任何一行逻辑。这是既定准则，不因"抽象成 skill"而放宽。

4. **文件输入走上传，不走 LLM 读表**
   前端加 Excel 上传控件，skill 拿到文件路径后用 `openpyxl` 读取；LLM **不解析表格内容**，只需知道"用哪个 skill、哪些参数"。涉密表格内容也不该进 prompt。

5. **写盘前回显确认**
   尤其生产网配置 / BOM，生成文件前回显参数让人拍板（延续 FDE 准则"先问再动手"）。

## 五、抽象落地步骤（待你确认后做）

1. **盘点 BAU 源码**：定位 Hub / Budget ROM / 4Blocker / PBT 各自的"引擎函数"入口，确认 UI 与逻辑的分界。
2. **抽 engine 模块**：把纯逻辑导出来，去掉 `tkinter` / `messagebox` 等 UI 依赖。
3. **写 skill 模块**：每个生成器一个 `SKILL` 定义 + `run()` 包引擎。
4. **注册进 orchestrator**：把 skill 注册表接进现有 `llm.py` 的调度，前端加"选技能 + 上传 Excel"入口。
5. **接 Office 落盘**：继续用 `openpyxl` / `python-docx`，或接 MCP Office。

## 六、待你提供 / 确认

- BAU 工程**源码路径**（尤其 PBT——我必须先读真实源码才能写它的 skill）。
- 2 个输入 Excel 的**字段契约**：哪个 sheet、哪些列映射到输出哪个字段。

## 七、执行顺序：先切片，后全量（重要）

**结论：方向对，但"先把所有功能都 skill 化"是错误节奏。** 正确做法：

1. **先打通一个端到端切片（thin slice）**
   选一个生成器（建议从最常用 / 最无风险的一个开始），完成：抽引擎 → 包 skill → 注册进 orchestrator → 前端加"选技能 + 上传 Excel" → 跑通"上传 → 路由 → 引擎生成 → 下载文件"全链路。这一步验证的是**整个管道模式**，不是某个生成器本身。

2. **管道 OK 后，按同一模板复制**
   其余生成器照葫芦画瓢，逐个包成 skill。每个只需改 `input_schema` 和 `run()` 调的引擎函数，结构不变。

3. **PBT 放最后，且带"读源码 + 实跑验证"闸门**
   绝不批量猜测。PBT skill 的执行体必须 import 已验证源码；在我读真实 PBT 源码并实跑通过前，不写它。

4. **MCP / Office 不是前置条件**
   第一切片可直接复用 Tkinter 工程里已有的 `openpyxl` / `python-docx` 引擎产出文件，不必等 MCP Office 层。MCP 是后续"让 LLM 动态改文档"的增强，不是 skill 化的门槛。

**一句话**：不要"全量 skill 化"一把梭；先让一个生成器在路线 D 上跑通闭环，模式验证后再铺开。这样既快又不会返工。

## 八、当下优先级：先盘点业务，不先搭界面

**结论：先了解业务（以现有 BAU 源码为事实依据），不要先铺界面。**

理由：
- 编排层（LLM 路由 / 双模 / 手动锁本地）已建成且通用，不需要业务知识，不必动它。
- 真正缺的是 skill 层（生成器），而它强依赖业务契约：每个生成器吃哪几个 Excel、哪些 sheet / 列、产出什么模板。界面（上传控件、表单字段）完全由这些契约决定。契约未知时先搭界面 = 必然返工。
- 符合既定工作流：先分析现状（只读源码）→ 代码证据表呈现 → 用户确认 → 再实现。绝不猜测（尤其 PBT）。

**当下第一步（Echo 阶段，只读不改）**：
1. 用户提供 BAU 工程源码路径。
2. 我盘点：定位 Hub / Budget ROM / 4Blocker / PBT 各自的"引擎函数"入口、输入输出契约。
3. 产出「代码证据表」（函数 → 输入文件 / 字段 → 输出模板 → 风险点），给用户确认。
4. 确认后，选一个生成器做第一个端到端切片（引擎抽取 → 包 skill → 最小界面上传 → 跑通管道）。

**一句话**：业务契约没摸清前，界面是空中楼阁；先把现有代码读透、出证据表，再动手。
